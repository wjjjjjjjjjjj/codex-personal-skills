# 流程模式参考

## 1. 知识图谱演示

适用于用户要求构造知识图谱、定义实体、生成图谱样例材料、做实体抽取或关系抽取测试的场景。

流程：
1. 选择一个一致的业务场景：项目、组织、事件、产品、人物或全生命周期。
2. 定义 4-6 个实体，每个实体包含：
   - 实体名称
   - 实体定义说明
   - 典型识别词/同义表达
   - 示例
3. 如有必要，定义 5-8 类关系。
4. 同步生成图谱抽取提示词，提示词必须围绕本次实体分类和关系类型定制，不得直接套用通用模板。
5. 生成 3-5 份 PDF，所有文件共享同一个业务世界，实体在不同语境中反复出现。
6. 同时包含表格和连续正文，便于测试结构化与非结构化抽取；用户要求内容丰富或加入图片时，读取 `references/visual-pdf-and-multimodal-compilation.md`，让图片与实体、状态或证据链发生业务关系。
7. 额外生成实体配置表，建议同时提供 Markdown 和 PDF。
8. 用文本抽取工具验证目标实体名称能在 PDF 文本层出现。

推荐文档组合：
- 项目全生命周期：项目概况、设计/批复说明、施工组织方案、系统集成方案、验收整改报告。
- 档案场景：全宗概况、分类方案、元数据标准、移交清单、利用记录。
- 组织图谱：企业概况、部门职责、项目名册、会议纪要、荣誉或通知材料。

图谱抽取提示词生成规则：
1. 开始编写前读取 `references/knowledge-graph-prompt-contract.md`。文件命名建议为 `图谱抽取提示词.md` 或 `[主题]知识图谱抽取提示词.md`。
2. 用户提供既有提示词样例、系统字段表或接口 JSON 时，把它视为输出契约。沿用章节顺序、JSON 字段名、占位符和约束表达，只替换当前主题的实体分类、专用约束、关系类型和完整示例。
3. 用户未提供 schema 时，默认结构固定为：
   - `# 角色`
   - `# 实体识别规则`
   - `## 实体处理约束`
   - `# 关系抽取规则`
   - `## 实体-关系-实体`
   - `# 输出格式`
   - `# 完整示例`
   - `# 执行指令`
4. 默认运行时 JSON schema 固定为：
   - `entities[]`：只含 `name`、`type`。
   - `relations[]`：只含 `source`、`target`、`relation_type`、`relation_time`、`evidence`。
   - 无明确关系时间时，`relation_time` 填字符串 `none`。
   - 不默认增加 `id`、`aliases`、`source_file`、`fact_boundary`、`source_id`、`target_id` 或属性对象。标准答案文件可以包含这些辅助字段，但不能污染运行时提示词 schema。
5. 实体识别规则必须列出本次分类，并强调 `type` 原样复制。示例中的实体类型全部来自该分类，不能出现未配置类型。
6. 实体处理约束至少包含同指合并、多级拆分、时间标准化和唯一标识；再按专题增加规则：
   - 人物：职务、任职机构、阶段、荣誉和成就的归因边界。
   - 工程：项目编码、标段编号、档号、问题编号、金额、地点、验收状态和整改闭环。
   - 机构：全称/简称、上下级机构和历史名称。
7. 关系抽取只发生在已识别实体之间。关系类型优先使用原文明示的动词或介词短语；语义归纳必须保持最小限度，不能凭共现推断股权、合同、承包、验收或隶属关系。
8. 完整示例必须同时给出“输入文档”和“输出”。输出是一段合法 JSON，不使用注释、伪代码或省略号。每条关系满足：
   - `source`、`target` 与 `entities[].name` 完全一致。
   - `relation_type` 使用目标系统要求的字段名，不得写成 `relation`。
   - `evidence` 逐字存在于示例输入文档。
   - `relation_time` 为标准时间或 `none`。
9. 执行指令保留 `{{档案原文}}` 或用户指定占位符，并明确“直接输出合法 JSON，禁止使用 Markdown 包裹，禁止添加解释”。提示词正文可以用 Markdown 编写，但模型运行时输出不能带代码围栏。
10. 抽取提示词控制在 5000 字以内。超长时优先压缩解释和示例关系数量，不删除固定章节、严格类型约束或完整 JSON 示例。
11. 交付前运行：

```powershell
python scripts/validate_graph_prompt.py <提示词.md> --types <实体类型1> <实体类型2> ...
```

只有长度、章节、JSON、字段集合、实体类型、关系端点、时间格式和示例证据全部通过时，提示词才可交付。

常见不可用输出及修正：

| 不可用表现 | 原因 | 修正 |
| --- | --- | --- |
| 使用 `relation` 而目标系统要求 `relation_type` | 字段名不兼容 | 严格沿用契约字段名 |
| 关系端点使用 ID，而系统按实体 name 建边 | 端点无法匹配 | `source`、`target` 使用实体标准全称 |
| 默认增加大量元数据字段 | 系统 schema 不接受 | 运行时 JSON 只保留默认字段 |
| 示例只写文字说明或含省略号 | 无法验证、无法直接复用 | 写完整合法 JSON |
| evidence 是概括句而非输入原文 | 关系不可追溯 | 逐字引用示例输入片段 |
| 提示词超过 5000 字 | 系统长度受限 | 压缩说明，保留契约和完整示例 |

### 1.1 领导人事任免知识图谱（独立子类型）

当用户提到领导任免、干部履历、职务变动、前任继任、机构更名后同一实体、主持工作与正式任命区分时，在通用知识图谱流程上追加读取 `references/leadership-appointment-graph-pattern.md`。

该模式固定使用人物、机构、事件、时空四类核心实体，并把职务作为人物动态履历和任免事件属性。它是新增领域子类型，不替换本节的工程项目、组织、档案或其他通用知识图谱模式。

最低演示判断点包括：

- 机构旧称与现名可依据更名文件、机构代码、全宗连续和有效期归一为同一节点。
- 合并新设、撤销并入、同名异地或只有语义相似的机构不得误合并。
- “主持工作”“负责日常工作”“代行职责”不等于正式任命。
- 决定日期与生效日期分别建模，任职时点查询以生效日期为准。
- 继任关系由同一归一机构、同一规范职务和前后时段顺接推理，并与单文档明示关系分开保存。

## 2. 智能编研演示

适用于用户要求生成“编研提示词 + 来源材料”，让模型自动形成验收报告、年鉴条目、专题报告、汇报材料或其他编研成果的场景。

流程：
1. 编写提示词，明确角色、输入材料、输出结构、约束条件和缺失信息处理规则。
2. 生成 4-6 份来源 PDF。不要把最终答案集中写在一份文件里。
3. 将必需事实分散到不同文件：背景、实施情况、评价意见、检测/调试记录、整改问题、资料清单等。
4. 至少加入一个需要判断的点，例如 `整改中`、`待确认`、版本不一致或缺失日期。
5. 检查模型使用提示词时是否必须跨文档综合，避免单文档改写即可完成。
6. 来源 PDF 包含图片或用户要求图文编研时，读取 `references/visual-pdf-and-multimodal-compilation.md`；同步生成图片资产清单，并在提示词中加入图片发现、稳定 ID、OCR/图像理解、图片筛选、正文回填、无 URI 降级和插图来源清单要求。

提示词必须包含：
- 角色设定
- 输入材料假设
- 编研目标
- 禁止编造规则
- 固定输出结构
- 来源可追溯要求
- 语气和风格要求
- 图片抽取与图文编研要求（当来源包含图片或用户要求图文输出时）

## 2.1 智能开放审核演示

适用于用户要求构造开放审核、开放鉴定、档案开放/限制判断、利用权限初审或多模态审核样例的场景。该模式与智能编研不同：核心不是生成一篇报告，而是让系统对待审核文档给出可解释、可回溯、可复核的初审结果。

开始前读取 `references/open-audit-pattern.md`。规则表与待审核文档必须作为两类独立输入，默认保留用户样例中的三列：`开放审核规则名称（暂定）`、`规则编号（拟定）`、`开放标志`。若目标系统只有这三列，匹配策略、证据要求和复核提示放到独立说明或标准答案中，不擅自污染接口字段。

数据构造要求：

1. 先建立规则表，再建立文档清单和审核标准答案；规则编号是三者之间的稳定引用键。
2. 待审核文档以连续段落和有业务作用的图片为主，表格作为补充。为段落、图片和表格建立稳定 ID、页码/章节定位和证据摘要。
3. 至少安排段落命中、图片命中、表格补充、开放类命中、无命中或边界待复核中的三类判断点，让演示体现多模态和人工兜底。
4. 规则名称不能只出现在规则表或标准答案中；待审核文档必须实际包含可被识别的段落、图片内容或表格证据。
5. 标准答案逐条保存 `文档编号`、`规则编号`、`预期命中`、`证据类型`、`证据定位`、`证据摘录`、`期望审核结论` 和 `判定说明`。图片命中必须能回指图片 ID，不能只写“图片中有相关内容”。
6. 将 `开放标志=开放/限制` 与单份文档的审核结论分开：规则属性是主数据，审核结论是本次文档初审结果；证据不充分或规则冲突时输出 `人工复核`。
7. 交付前运行 `scripts/validate_open_audit_bundle.py --rules <规则表.csv> --documents <文档清单.csv> --ground-truth <审核标准答案.csv>`，并对 PDF/图片按当前 PDF 或多模态规则做文本和视觉检查。

推荐交付物：规则 CSV、文档清单 CSV、审核标准答案 CSV、待审核文档目录、图片清单（如有）、说明文件和校验结果。不要把审核标准答案当成实际待审核文档，也不要只生成几张空白图片来代替证据。

## 3. 人物或机构专题演示

适用于用户要求做人物生平、领导画像、机构沿革、任职阶段、身份标签、主要成就或时间线展示的场景。

流程：
1. 真实人物或机构必须先核验公开事实。核验不足时，明确标注哪些内容来自用户提供前提。
2. 做多来源资料发现：优先使用官方网站、任免文件、政府/国资平台、正式公告和原始档案，其次使用有署名、日期和原始出处的权威媒体。通用搜索引擎、百科和搜索摘要只作发现线索，不能仅凭排名判定为事实。
3. 创建统一字段 schema，例如：
   - 姓名/机构名称
   - 字号/别名
   - 时期
   - 生卒年/成立时间
   - 籍贯/所在地
   - 生平概述/机构概述
   - 身份标签
   - 主要成就
   - 来源说明
4. 对字段做可用性分级：
   - 🟢 直接可用：如姓名、明确别名、明确任职机构。
   - 🟡 可推断：如“约2020年代至今”“改革开放以来”等粗颗粒度时期。
   - 🔴 严重缺失：如公开资料未见出生年份、籍贯、早年经历。
5. 按时期、角色、机构、项目主题或成就主题拆分 PDF。
6. 通用字段在多份文档中保持一致。
7. 不要把机构成就直接写成个人成就，除非来源明确支持。优先使用 `任职阶段关联`、`所在集团`、`其任职机构` 等审慎表述。
8. 生成 CSV 或 Markdown 结构化表，便于系统测试字段聚合。


人物/机构专题的来源判定规则：
- 🟢 可直接引用事实：官方网站、任免文件、政府/国资平台、正式公告、原始档案或可追溯权威媒体中明确列出的字段，如出生年月、籍贯、毕业院校、现任职务、任职时间。
- 🟡 待核验线索：搜索摘要、转载页面、论坛问答、自媒体文章、无来源聚合页。可用于扩大检索词，不直接写入事实字段。
- 🔴 不采用：无法打开的页面、来源不明图片、同名人员信息、与人物/机构关系无法确认的结果。
- 多个搜索摘要或百科条目相同不等于独立证据；至少要有一个可追溯的一手或权威页面明确列出该字段，才能提升为“可直接引用事实”。
- 引用搜索获得的信息时，在目录或说明文件中写明“来源线索”，至少保留页面名称和 URL。
人物专题的二次优化经验：
- 如果某字段根源缺失，不要在每份 PDF 中重复长篇解释；在字段表中明确一次即可。
- 生平概述不能只写“资料缺失”，应围绕可支撑的时代背景、任职机构、业务主题和审慎成就写 200-300 字。
- 身份标签是展示价值最高的字段之一，应从多份文档中去重合并，形成 10-20 个标签。
- 主要成就应按阶段拆分，每条 50-100 字，使用“集团成果关联任职阶段”的口径。
- 新版重构应单独输出到新目录，保留旧版用于对比系统优化效果。

未知字段推荐写法：
- `公开资料未见明确披露。`
- `用户提供信息，待正式来源核验。`
- `截至 YYYY-MM-DD 按在任公开人物处理。`
- `出生年份：公开资料未见明确披露。当前状态：按截至日期的公开资料核验。`

## 4. 以图搜图 / 照片档案演示

适用于用户要求做图片检索、人脸检索、一寸照匹配、照片档案匹配或相关样例数据的场景。

流程：
1. 优先使用用户提供图片或官方公开来源图片。
2. 真实人物必须先通过可靠来源确认身份，再下载图片。
3. 每张图片保存来源清单：文件名、来源 URL、页面标题、访问日期、为什么认为包含目标人物。
4. 区分参考照和待检索照片档案。
5. 身份不确定时标注 `候选图片，身份未核验`，不要写成已确认。
6. 不抓取私人社交媒体图片，不绕过访问限制。

推荐交付物：
- `reference/` 参考头像或一寸照
- `archive_photos/` 多人合影或活动照片
- `manifest.csv` 来源清单
- `说明.md`，说明核验口径和风险

## 5. 字段质量评估表

当用户给出字段要求，或生成结果需要复盘时，输出或内置类似评估表：

| 字段 | 效果 | 处理建议 |
| --- | --- | --- |
| 姓名 | 🟢 直接可用 | 原文明确值，放入所有文件固定字段表。 |
| 字号/别名 | 🟢 直接可用 | 未提及时填“无”，不要留空。 |
| 时期 | 🟡 可推断 | 给出粗颗粒度时期，并说明精度限制。 |
| 生卒年 | 🔴 严重缺失 | 分开写“出生年份：公开资料未见明确披露”“当前状态：按截至日期的公开资料核验”，不编造。 |
| 籍贯 | 🔴 严重缺失 | 写“公开资料未见明确披露”。 |
| 身份标签 | 🟢 丰富可用 | 多文档提取、去重合并、形成标签集。 |
| 主要成就 | 🟡 可用但需审慎 | 使用“任职阶段关联”表述。 |
| 生平概述 | 🟡 可重构 | 不重复缺失说明，围绕可支撑主题形成概述。 |

## 6. PDF 生成与质检

生成 PDF 时：
1. 使用 reportlab 或项目内已有文档工具。
2. 注册中文字体，如 NotoSansSC、微软雅黑、宋体或等线。
3. 包含标题、表格和连续正文段落；图文增强模式通常控制为 2-4 页、800-1800 个可抽取中文字符，不能用空白或重复语句凑页。
4. 尽量写入标题、作者、主题等元数据。
5. 使用 pdfplumber 或同类工具验证文本可抽取。
6. 在最终回复中报告验证结果。
7. 用户要求加入图片或编研需抽取图片时，至少嵌入一张有业务作用的图片，生成图片ID、图题、来源/生成方式、关联材料、事实边界和编研候选状态。
8. 运行 `scripts/validate_visual_pdf_bundle.py` 检查页数、字符数、内嵌图片和文本层；运行 `scripts/validate_multimodal_compilation.py` 检查图文编研提示词。

最低质检清单：
- 每份相关 PDF 中出现目标字段或实体。
- 中文文本可正常抽取。
- 文件名有业务含义。
- 输出文件归入清晰目录。
- 真实世界不确定信息已明确标注。
- 二次优化版本必须能与旧版区分。
- 图片未变形、未越界，图注和事实边界可抽取。
- 关键事实同时存在于文本层，图片不是唯一证据。
