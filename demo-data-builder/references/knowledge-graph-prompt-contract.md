# 知识图谱抽取提示词兼容性契约

## 为什么要单独定义契约

知识图谱提示词不是普通说明文。目标系统通常按固定字段解析 JSON：字段名、层级或端点表达稍有变化，即使语义正确也无法导入。过去常见问题是把标准答案需要的丰富字段直接塞进运行时 schema，生成了 `id`、`aliases`、`source_file`、`fact_boundary`、`relation` 等字段，和系统实际要求的 `name`、`type`、`relation_type` 不一致。

因此，每次先锁定接口，再写抽取规则和示例。

## 契约优先级

按以下顺序决定最终格式：

1. 用户提供的完整提示词样例。
2. 用户提供的系统接口文档、字段表或 JSON 示例。
3. 本文件的默认契约。

高优先级内容存在时，逐字沿用章节、字段名、占位符和输出层级。不要“优化”为另一种自认为更标准的格式。

## 默认章节结构

用户未指定时使用以下结构和顺序：

1. `# 角色`
2. `# 实体识别规则`
3. `## 实体处理约束`
4. `# 关系抽取规则`
5. `## 实体-关系-实体`
6. `# 输出格式`
7. `# 完整示例`
8. `# 执行指令`

标题本身也是回归校验的一部分，不要随意改成“任务说明”“抽取要求”等近义标题。

## 默认运行时 JSON schema

```json
{
  "entities": [
    {
      "name": "实体标准全称",
      "type": "实体分类列表中的原始值"
    }
  ],
  "relations": [
    {
      "source": "源实体name",
      "target": "目标实体name",
      "relation_type": "关系类型",
      "relation_time": "标准时间或none",
      "evidence": "支撑关系的原文片段"
    }
  ]
}
```

默认不增加任何字段。实体配置表、标准答案和质检文件可以保留 ID、别名、来源文件等辅助字段，但运行时提示词不能自动继承这些字段。

## 各章节必须解决的问题

### 角色

说明专题范围、抽取目标和目标系统可解析的 JSON 输出。角色段保持简短，不写业务背景长文。只有明确交付 Neo4j 导入格式时，才另行生成节点/关系 CSV 或 Cypher，并声明具体导入契约。

### 实体识别规则

列出本次实体分类、定义和典型边界。明确 `type` 必须逐字复制，不能翻译、缩写或创造新类型。

默认控制在 4-6 个实体类型。这里指“类型数量”，不是最终抽取出的节点数量。

### 实体处理约束

至少包含：

- 同指合并：标准全称、简称、旧称如何归并。
- 多级拆分：机构、项目、标段、设施、文件等层级不得粘成一个长实体。
- 时间标准化：明确日期、年月、季度和相对时间的处理。
- 唯一标识：默认使用实体 `name` 作为节点唯一标识。

根据领域增加专用规则：

- 人物：人物、职务、任职机构、阶段、荣誉、成就的归因边界。
- 工程：项目编码、标段编号、档号、问题编号、金额、地点、状态和整改闭环。
- 机构：上下级机构、历史名称、简称和部门拆分。

### 关系抽取规则

只在已识别实体之间建边。优先使用原文明示动词或介词短语。原文没有明确关系词时，只做可由上下文唯一确定的最小归纳，不因共现推断股权、合同、承包、隶属、任职或验收关系。

`source`、`target` 必须与实体 `name` 完全一致。无关系时间填字符串 `none`，不要填空值、null 或“未知”。

### 输出格式

明确要求运行时直接输出合法 JSON，不使用 Markdown 代码围栏，不添加注释、说明或前后缀。提示词文档中的示例可以放在代码围栏内，模型最终输出不能带围栏。

### 完整示例

示例必须来自同类业务场景，并包含：

1. 一段完整输入文档。
2. 一段可被 JSON 解析器直接解析的完整输出。
3. 示例实体类型全部来自本次分类。
4. 每条关系端点都能在实体数组中找到同名实体。
5. 每条 `evidence` 都逐字存在于示例输入。
6. 不使用 `...`、`……` 或注释代替内容。

示例不必穷举所有实体和关系。优先保留能展示同指合并、层级拆分、时间和证据规则的 6-10 个实体、6-12 条关系，使全文控制在 5000 字以内。

### 执行指令

保留目标系统占位符。默认写法：

```text
# 执行指令
现在处理以下文档，直接输出JSON结果：

{{档案原文}}
```

## 默认模板骨架

```text
# 角色
你是一个专业的[专题]知识图谱信息抽取引擎，从给定文档中精确提取实体与关系，输出目标系统可解析的结构化 JSON。

# 实体识别规则
仅识别以下类型的实体，忽略不属于任何类型的内容：
[逐项列出实体类型、定义和示例]

【严格约束】实体的type字段必须从上述列表中原样复制……

## 实体处理约束
[同指合并、多级拆分、时间标准化、唯一标识、领域专用约束]

# 关系抽取规则
仅在已识别的实体之间抽取关系。

## 实体-关系-实体
[关系提取、推断边界、relation_time、evidence规则]

# 输出格式
直接输出合法JSON，禁止使用markdown包裹，禁止添加注释。
[插入默认或用户指定的完整JSON结构]

# 完整示例
输入文档：
[示例原文]

输出：
[完整合法JSON]

# 执行指令
现在处理以下文档，直接输出JSON结果：

{{档案原文}}
```

## 禁止的默认偏离

- 把 `relation_type` 支成 `relation`。
- 用 `source_id`、`target_id` 代替名称端点。
- 给实体默认增加 `id`、`aliases`、`attributes`、`source_file`、`fact_boundary`。
- 给关系默认增加 `confidence`、`source_file` 等系统未要求字段。
- 示例用文字说明替代 JSON，或用省略号省略实体和关系。
- evidence 使用模型概括句而不是输入原文。
- 把“整改中”“有条件通过”“计划完成”抽取为“已关闭”“已验收”“已竣工”。

## 交付前质量门槛

运行：

```powershell
python scripts/validate_graph_prompt.py <提示词.md> --types <类型1> <类型2> ...
```

全部检查通过后再交付。校验器检查字符数、固定章节、JSON合法性、字段集合、实体类型、名称唯一性、关系端点、时间格式、示例证据和 `{{档案原文}}` 占位符。
