## 1. 主张分级

为重要表述选择一种状态：

| 状态 | 含义 | 可用写法 |
|---|---|---|
| 已确认事实 | 用户或可靠来源明确给出 | 直接陈述并保留来源 |
| 产品能力 | 公司产品资料能够支持 | 使用正式产品名称和能力口径 |
| 合理推断 | 由现状推导但未验证 | “据现有资料判断”“可能” |
| 建议方案 | 本方案提出的设计 | “建议采用”“本期可按” |
| 待确认 | 依赖客户、第三方或测试 | “需在……后确认” |

不要用确定语气包装推断或建议。

## 2. 来源使用

- 用户原始资料用于证明客户事实、现状和要求。
- 公司知识库用于证明产品能力、实施方法和正式命名。
- 政策标准原文用于证明条款，不使用二手文章代替。
- 客户公开资料用于补充背景，不能替代项目现场事实。
- 行业经验用于提出建议，不能伪装成客户已确认情况。
- 招标文件证明“采购方要求什么”，不证明“供应商一定能做到”。
- 案例必须能够核验客户、范围和成效。证据不足时不写具体客户名或数字。

引用外部资料时保留标题、发布主体、日期和链接。引用标准条款时核对版本和适用范围。

## 3. 产品与客户需求

- 使用公司知识库中的正式产品和组件名称。
- 用户提供需求内容时，先建立内部“需求—产品—能力—匹配程度—方案写法”映射，再起草方案正文。
- 优先将客户语言映射到安铂现有产品和已验证功能，不随意创造新平台、新模块或新版本。
- 匹配程度分为“标准能力、扩展能力、能力缺口、第三方依赖”。标准能力优先使用；其余三类必须写清边界，不能混写成现成功能。
- 需求超出现有能力证据时，标记为定制开发、待评估、第三方能力或不在本期范围。
- 对“支持、兼容、无缝、自动、实时、智能、全量”等词保持审慎，说明对象、条件和程度。
- 技术路线必须解释如何绕开或处理既有系统约束，不能只写“对接”。
- 功能清单、知识库、白皮书和内部映射表用于内部核验。客户成稿只呈现经核验后的项目能力、业务作用和边界，不说明内部取材过程。

## 4. 报价、接口和实施边界

每个费用项至少对应：

- 范围和数量
- 软件、服务、硬件或第三方属性
- 交付物
- 主要前提
- 验收结果
- 不包含项

不要把平台总价作为无法解释的黑箱。优先把价格分配到具体应用、组件、接口、数据治理或服务。

接口承诺至少说明：

- 对方是否开放接口和提供规范
- 网络、账号、测试环境和样例数据是否可用
- 数据映射、联调和异常处理由谁负责
- 第三方厂商改造费是否包含
- 规范未知的接口是否需另行评估

实施费、数据迁移、数据治理和纸质档案数字化加工是不同范围，必须分开说明。

## 5. 档案 AI 边界

默认采用以下原则：

- 先治理再智能：数据质量不足时先做元数据、文本、关联和权限治理。
- 结果可追溯：摘要、问答、报告和知识图谱应能回到原始档案或证据片段。
- 关键判断人工复核：AI 提供辅助结果，不替代分类、鉴定、开放审核、销毁审批等责任性判断。
- 明确部署域：涉密、非密、互联网和内网数据不能混写，模型调用和数据外发条件必须明确。
- 明确效果条件：识别率、准确率、响应时间取决于数据质量、模型、硬件和测试集，未经测试不承诺数字。
- 明确生成内容定位：AI 输出是辅助材料或建议稿，正式结论按客户制度审核签发。

## 6. 三维与数据治理类高风险表述

- 设计模型不等于产品实例的竣工状态。
- 格式转换成功不等于几何、装配、PMI 或语义信息无损。
- 轻量模型是利用入口，不是生产、质量或权威归档凭证。
- 供应商可对接收、转换、检测和关联负责，不能补造上游从未形成的数据。
- “数字孪生”不能自动扩展为实时监控、仿真或预测维护，除非范围和数据条件已确认。
- 数据治理平台能够检查、校验和编排，但历史元数据缺失往往仍需要人工治理。
- 第三方系统不可改时，评估通过受控中间库或治理库解耦，不直接承诺改造成功。
