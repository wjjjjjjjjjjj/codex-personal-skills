# 方案结构选择手册

根据决策场景选择结构。以下是论证骨架，不是必须照抄的目录。

## 目录

1. 领导决策或立项报告
2. 营销型解决方案
3. 技术建设方案
4. 小型正式呈报材料
5. 既有方案增补或重构
6. 结构选择检查

## 1. 领导决策或立项报告

### 适用

集团高层、政府领导、项目立项会、预算决策会。读者关心是否值得做、做什么、花多少、风险是否可控。

### 推荐逻辑

1. 建设背景与必要性
2. 现状及核心管理问题
3. 建设目标
4. 总体思路
5. 建设内容与业务价值场景
6. 建设成效
7. 投资估算
8. 实施计划与保障

### 写作判断

- 把“买系统”提升为治理工程、业务证据工程或数据能力建设。
- 明确为什么现在做以及不做的风险。
- 价值场景分两层写：需求分析回答哪些业务问题需要支撑；建设内容回答如何落地。
- 正文以段落为主，只保留投资和实施阶段等必要表格。
- 不使用招投标式逐项功能响应。

## 2. 营销型解决方案

### 适用

客户交流、产品方案、升级改造、商机推进。目标是建立共识并推动下一步。

### 推荐逻辑

1. 客户业务困境
2. 需求与目标结果
3. 总体方案和技术路线
4. 场景化建设内容
5. 差异化能力
6. 业务价值
7. 实施与风险控制
8. 经核验的案例或公司信任

### 写作判断

- 每个模块使用“客户痛点 + 对应能力 + 业务结果”。
- 差异化能力单独突出，不埋在常规功能中。
- 案例只使用已核验事实；无法核验的数字不写。
- 不把公司介绍放在问题和方案之前。

## 3. 技术建设方案

### 适用

已进入技术论证、设计或实施准备阶段，需要说明业务流程、数据、架构、接口、部署和验收。

### 推荐逻辑

1. 项目背景和设计依据
2. 需求分析
3. 建设目标和原则
4. 总体架构与建设逻辑
5. 业务与应用建设
6. 数据治理或数据资源建设
7. 技术架构、部署与安全
8. 接口与迁移
9. 实施、培训和运维
10. 验收方法、风险和边界

### 写作判断

- 用业务链和数据流解释架构，不从技术名词开始。
- 将功能还原为业务场景、管理问题和能力诉求。
- 公共组件说明可被哪些系统复用，不重新包装成多个独立平台。
- 明确前置条件、输入数据、异常处理、责任主体和验收结果。
- 采购要求不等于我方产品能力，能力必须有公司证据。

## 4. 小型正式呈报材料

### 适用

金额较小、范围清晰、需要快速呈报的政府机关或企事业项目，常见篇幅为 4—8 页。

### 推荐逻辑

1. 建设背景
2. 核心需求
3. 建设目标
4. 建设内容
5. 投资估算
6. 实施要点

### 写作判断

- 不为了显得完整增加空泛的建设原则、附件或冗长公司介绍。
- 篇幅短但必须回答为什么建、建什么、多少钱、怎么落地。
- 短方案可以压缩文字，不能丢失产品边界、接口条件和验收结果。
- 客户提供参考稿时，内容口径服从公司知识库，视觉与公文格式服从客户参考。
- 用户要求“公文格式”“仿宋”或“大理州政协那套格式”时，读取 `official-document-format.md`；公文版式不自动等于固定四页，篇幅仍由决策场景决定。

## 5. 既有方案增补或重构

### 适用

补写章节、按意见修改、重大重构、从功能清单反推需求、将长方案压缩为汇报稿。

### 推荐步骤

1. 明确允许修改的章节、对象和目标。
2. 提取原文层级、术语、产品名称和引用口径。
3. 建立“原内容—问题—修改策略—新内容”映射。
4. 只修正范围内内容，保留其他章节和用户已有修改。
5. 检查同名功能在不同系统中的业务含义，不跨场景套写。
6. 全文搜索客户名、项目编号、采购人、旧价格和旧版本残留。

重大重构先提交新旧结构对照和完整内容大纲。PPT 重构必须先走逐页内容确认。

## 6. 结构选择检查

选择结构前回答：

- 决策人最先需要判断什么？
- 读完后要采取什么动作？
- 失败时谁承担责任？
- 方案是推动共识、完成立项、证明可实施，还是逐项响应？
- 哪些章节对当前决策没有贡献，可以删除？
