# 安铂 PPT 咨询逻辑与内容锁定

本文件吸收 CyberPPT 的证据链、SCR 和内容锁定机制，并按安铂售前汇报场景降级为可执行的轻量流程。它解决的问题是：PPT 不是把材料排漂亮，而是把客户能够接受的业务判断、证据和行动路径做成可交付页面。

---

## 一、适用场景

以下任务必须使用本文件：

- 根据客户材料、方案说明、调研纪要生成 PPT；
- 编写售前解决方案、汇报材料、投标演示、项目汇报；
- 用户只给一句话，但期望产出完整安铂风格 PPT；
- 材料中包含数字、阶段、系统模块、业务痛点、项目背景或客户诉求。

纯样式演示、内部培训小课件、只做封面/单页美化时，可只使用视觉规范和质量门槛。

---

## 二、证据表：先把材料变成可审计判断

正式写页面前，先建立轻量证据表。没有原始材料时，也要把“用户已明确给出的信息”和“模型合理补齐的行业假设”分开。

| ID | 论点/数据/诉求 | 来源位置 | 置信度 | 风险或 caveat | 业务含义 | 推荐视觉 |
|---|---|---|---|---|---|---|
| E01 | 客户希望提升档案归档与利用效率 | 用户输入/材料章节 | 高 | 缺少量化基线 | 应从效率提升转向治理能力建设 | 痛点诊断 + 流程图 |
| E02 | 现有系统分散、门类不统一 | 材料/访谈摘要 | 中 | 需确认系统数量 | 方案应强调统一数据底座 | 多层架构图 |

规则：
- 数字、年份、金额、客户名称、政策条款不得编造；缺失就标“待补充”。
- 可以补行业通用判断，但必须标注为“行业假设/售前推断”。
- 每个强结论至少要有 1 条证据或 1 条明确业务假设支撑。
- 有冲突的来源不静默合并，必须保留差异并在 PPT 中选择保守表达。

## 三、SCR：把页面组织成决策逻辑

安铂售前 PPT 默认使用 SCR，而不是功能目录：

- **Situation 稳定背景**：客户已经接受的现实，如政策要求、档案数字化趋势、组织管理现状。
- **Complication 关键矛盾**：不解决会造成什么风险、低效、不可控或机会损失。
- **Resolution 解决路径**：安铂方案如何以可落地能力解决矛盾，并带来业务结果。

### 3.1 一句话需求的默认 SCR

当用户只说“做一份某某 PPT”时，不要复用固定业务结论，必须先按任务类型生成 SCR：

| 任务类型 | Situation | Complication | Resolution |
|---|---|---|---|
| 售前解决方案 | 客户处在档案数字化、数据治理或业务协同升级阶段 | 现有管理方式与目标能力之间存在差距，影响效率、合规、利用或治理 | 用安铂方案说明建设路径、能力组合和可落地价值 |
| 产品/系统介绍 | 客户需要理解产品能解决什么业务问题 | 如果只列功能，客户难以判断产品与自身场景的关系 | 用场景、能力、架构、演示路径证明产品价值 |
| 内部/领导汇报 | 决策者需要快速判断是否做、怎么做、风险如何控 | 信息过细会稀释判断，信息过少又无法支撑拍板 | 用结论、依据、方案、风险控制、下一步事项组织页面 |

默认 SCR 只能作为推理框架，不能把“档案数据底座 + 智能利用 + 治理运营”固定写进每一份 PPT。客户行业、汇报目的、材料内容不同时，SCR 必须随内容重构。

### 3.2 结论标题规则

页面标题必须尽量是“可辩护判断”，不是栏目名。

弱标题：
- 项目背景
- 系统架构
- 功能介绍
- 建设路径

强标题：
- 档案管理的核心矛盾正在从“有没有系统”转向“能否形成统一数据底座”
- 平台架构需要同时支撑业务流转、数据治理和智能利用三类能力
- 分阶段建设可以降低一次性改造风险，并让业务部门更早看到价值

## 四、页面内容锁定 slide_content_lock

生成 PPT 前，必须先按 `pre-generation-content-approval.md` 向用户输出完整逐页主要内容稿，并取得确认。确认后才为每页锁定真实内容，防止后续排版时任意删减或改写。轻量版不要求写 JSON 文件，但内部必须有同等结构；复杂项目建议落成文件。

每页至少锁定：

| 字段 | 说明 |
|---|---|
| slide_id | 页码 |
| page_question | 本页主要说明的问题 |
| problem_explanation | 对应问题解释，说明背景、因果或业务影响 |
| arguments | 阐述论据；每条标注 evidence_id 和来源状态（事实/用户输入/行业假设/待确认） |
| role | Situation / Complication / Resolution / 承接 / 收束 |
| conclusion_title | 结论标题 |
| evidence_ids | 支撑证据 ID |
| required_content | 不得删减的核心文字、数字、模块、表格项 |
| visual_type | 图表、矩阵、流程、分层、对比、路线图等 |
| layout_signal | 内容信号：阶段、层级、比较、数据、场景、政策映射、风险保障等 |
| layout_family | 动态版式家族：诊断、架构、能力地图、流程、矩阵、数据证据、故事板、风险闭环、映射表、SO WHAT 总结等 |
| layout_reason | 为什么该内容必须使用这个版式，而不是默认封面/目录/卡片/结束页 |
| components | 主图、侧栏、标签、SO WHAT、页脚、来源等 |
| caveat | 需要保守表达或待确认的信息 |
| editable_required | 必须可编辑的文字/数字/图表标签 |
| content_plan_version | 已确认内容稿版本 |
| approval_status | `confirmed` 或用户明确豁免 `waived_by_user` |

简化示例：

```json
{
  "slide_id": 5,
  "page_question": "为什么平台架构不能只列功能模块？",
  "problem_explanation": "多门类档案和跨系统业务需要明确层级、数据流和安全边界，功能清单无法表达依赖关系。",
  "arguments": [{"claim": "现有系统分散、门类不统一", "evidence_id": "E02", "source_status": "sourced"}],
  "role": "Resolution",
  "conclusion_title": "平台架构必须以统一数据底座承接多门类档案与跨系统业务流转",
  "evidence_ids": ["E02", "E05"],
  "required_content": ["应用层", "能力层", "数据层", "安全与标准体系"],
  "visual_type": "多层横向架构",
  "layout_signal": "系统/层级/平台底座",
  "layout_family": "架构分层",
  "layout_reason": "内容核心是平台、应用、数据之间的层级支撑关系，适合用架构分层而不是卡片平铺",
  "components": ["主架构图", "右侧能力说明", "底部 SO WHAT"],
  "caveat": "具体对接系统数量待客户确认",
  "editable_required": ["标题", "层级标签", "模块名称", "SO WHAT"],
  "content_plan_version": "v1",
  "approval_status": "confirmed"
}
```


动态版式字段是硬约束：`visual_type` 只能说明图示形态，`layout_signal / layout_family / layout_reason` 才能说明页面为什么应该长成这样。缺少这三个字段，或没有已确认的内容稿版本时，不得进入最终页面生成。

## 五、页面信息密度与组件清单

每页计划不能只写标题。必须写出信息区数量和组件结构。

| 页 | 结论标题 | 主视觉 | 信息区 | 必备组件 | 低密度风险 |
|---|---|---|---|---|---|
| 3 | 当前问题不是缺工具，而是缺统一治理闭环 | Before/After 双列 | 4 个痛点 + 4 个目标 | 痛点列、箭头、目标列、底部结论 | 若痛点只有短词，需补场景解释 |
| 6 | 核心能力应围绕采集、治理、利用、监管形成闭环 | 中心辐射/闭环 | 中心 1 + 周边 4 | 中心结论、4 能力、连接线、图标 | 防止做成 4 张普通卡片 |

低密度页面必须处理：
- 增加证据、例子、输入输出、风险提示或 SO WHAT；
- 改版式，不是简单拉大卡片；
- 必要时合并或拆页。

## 六、视觉系统锁定

安铂不默认展示 CyberPPT 的 8 种风格样张。默认视觉系统已经锁定为安铂商务风：

- 色板：`#004D85`、`#003B66`、`#F9904E`、`#F8FAFC`、Slate 灰阶。
- 页面尺寸：16:9，`13.33 x 7.5`。
- 字体：Noto Sans SC / 微软雅黑备用。
- 页面表面系统：浅蓝灰底 + 深蓝结构条 + 白色/浅色内容面板 + 橙色焦点。
- 图表语言：蓝橙双主色、直接标签、低网格、强解读。
- 图标语言：同一套线性 SVG 或同一套几何徽章，禁止混用。

只有用户明确要求探索“不同视觉方向”时，才可以借鉴 CyberPPT 的“风格样张确认门”，但必须将候选风格改造成安铂可接受的分支，例如：商务标准、商务高密度、极简高管、产品科技、投标稳重、数据分析。不得直接使用 CyberPPT 的红/绿/紫/米色咨询色板替代安铂 VI。

## 七、轻量 manifest 与 QA 记录

正式交付 PPT 时，至少在最终回复或交付目录中形成轻量记录，复杂项目建议写入 `slide_manifest.json`。

每页记录：

| 字段 | 要求 |
|---|---|
| slide_id | 页码 |
| layout_type | 使用的版式类型 |
| visual_focus | 视觉主角 |
| evidence_ids | 证据 ID 或“行业假设” |
| native_components | 原生文本、形状、表格、图表 |
| image_assets | 图片、Logo、截图、SVG；说明必要性 |
| typography_check | 标题、正文、注释是否符合层级 |
| qa_status | pass / rework |
| rework_reason | 若返工，说明原因 |

交付前必须确认：
- 主要标题、正文、关键数字、图表标签、页脚可编辑；
- 图片只用于 Logo、截图、照片、复杂装饰或 SVG 图标，不承载主要文字；
- 图表、流程、矩阵、SO WHAT 优先使用原生对象重建；
- 渲染图中无溢出、错位、空白失衡、风格漂移。

## 八、安铂版双硬门槛

每页同时通过两个门槛才算合格：

1. **可编辑信息层**：客户后续能在 PowerPoint 中直接修改标题、正文、模块名、关键数字、图表标签、注释、页脚和 SO WHAT。
2. **视觉语义层**：页面的业务结构、阅读顺序、图示关系、颜色层级、空间重心和品牌质感没有因为可编辑性被降级。

失败例子：
- 为了可编辑，把方案架构做成几行普通矩形，丢失层次和主视觉。
- 为了好看，把整页做成图片，客户无法改文字。
- 为了省事，把流程、矩阵、关系图都改成三张卡片。
- 为了避免图片，把产品截图或客户 Logo 手绘成低质图形。

## 九、图标库策略

CyberPPT 已内置大规模 SVG 图标库。当前机器存在 `C:/Users/se7en/.codex/skills/CyberPPT/assets/icons/` 时，安铂 PPT 可以优先复用其 SVG 图标，但必须遵守安铂取色和风格统一规则。

推荐：
- 商务/简约风：优先 `tabler-outline`，统一线性描边；
- 扁平风：可用 `tabler-filled` 或 `chunk-filled`；
- 科技风：可用 `phosphor-duotone` 或线性图标改霓虹色；
- `simple-icons` 仅用于真实品牌 Logo。

使用时锁定一个图标库，不跨库混用。图标颜色统一改为 `#004D85` 或 `#F9904E`；深色页可用白色或浅蓝。
