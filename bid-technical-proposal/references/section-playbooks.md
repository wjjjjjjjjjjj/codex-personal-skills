# 技术标章节编写手册

## 何时读取本文件

在追溯矩阵完成初步拆解后，按当前要写的章节读取对应部分。不要为了写一个功能响应而加载全部章节打法。

快速选择：

| 当前任务 | 读取部分 |
|---|---|
| 逐条功能响应 | “响应状态写法”与“功能和场景章节” |
| 按评分点写方案 | “评分项响应单元” |
| 写架构、安全、集成、迁移 | 对应专题章节 |
| 写实施、测试、培训、运维 | “交付型章节” |
| 做档案信息化技术标 | 再读取 `references/domains/archive-informatization.md` |
| 审稿 | “反模式和自检” |

## 通用写作单位

每一个可独立评审的响应单元按需包含六类信息：

1. **响应结论**：明确能力状态，不用模糊形容词；
2. **实现机制**：说明由什么组件、流程、角色或控制措施实现；
3. **项目化落点**：说明在本项目的对象、范围、配置、接口和实施位置；
4. **验证方式**：说明如何测试、验收或用证据证明；
5. **条件与边界**：说明依赖、前提、排除项和责任分工；
6. **业务结果**：解释降低什么风险、改善什么流程，但不得添加无依据数字。

六类信息不是固定六段。简单客观条款可以一段完成；高分、高风险、证明复杂的条款应展开为小节、表格或图。篇幅由“分值、满分条件、风险、证明难度”决定，不按“每分几页”或“每章至少几页”机械分配。

## 响应状态写法

正文用语必须与追溯矩阵的能力、证据、承诺和偏离状态一致。以下小节标题是面向正文的“响应类型”，不是另建一套台账状态：

- “完全支持”仅对应 `能力状态=已具备`、`证据状态=已核验可引用`、`偏离状态=无偏离`；
- “条件响应”对应 `能力状态=条件具备` 和 `偏离状态=条件响应`；
- 其余类型直接沿用能力状态，并同步登记偏离和承诺状态。

### 完全支持

使用条件：现有能力覆盖全部要求，证据有效且适用于本项目。

建议结构：

> 我方完全满足该项要求。系统通过【具体机制】实现【要求对象与动作】，在【本项目范围】中配置为【项目化落点】；通过【测试/证据】验证。

禁止只写“完全响应、无偏离”而没有实现机制。若招标要求逐条响应表，可在结论列写“完全满足”，并在技术说明列给出机制和证据索引。

### 条件响应

必须把条件写在结论附近，不能藏在章节末尾。

> 在【环境、接口、数据或客户配合条件】具备的前提下满足该项要求。我方负责【责任】，招标人/第三方需完成【责任】；若条件未满足，将影响【范围、进度或效果】，拟通过【补救措施】控制。

不得写成“完全满足，前提是……”。条件构成响应边界，应在台账中记为 `条件具备` 和 `条件响应`。

### 定制实现

> 该能力纳入本项目定制实现范围，不属于当前基线产品的直接配置能力。拟通过【设计/开发方案】完成，责任边界为【边界】，计划在【已确认阶段或里程碑】交付，并通过【验收方式】验证。

只有在范围、工期、资源和商务影响得到相应责任人确认后才能进入提交候选版。未确认时能力状态保持 `待核验`、承诺状态保持 `待审批`，不能写确定性交付日期。

### 第三方依赖

> 该项能力由【第三方系统/服务】提供，我方通过【接口或集成方式】实现协同。第三方需提供【接口、许可、环境、数据或服务条件】；我方承担【集成责任】，不承担【明确排除责任】。

必须说明第三方产品、许可、费用和 SLA 是否纳入投标范围；不能把第三方能力写成自有产品能力。

### 不支持

> 当前产品及本项目已确认范围不能满足【具体差异】。可选替代路径为【替代方案】，其对【评分、范围、进度、费用或验收】的影响为【影响】。

若不允许负偏离，强制项/否决项出现 `不支持`、`条件响应` 或 `负偏离` 时必须阻断提交。项目负责人只能通过补足能力与证据、取得采购方有效变更或将内容依法移出本次范围来关闭，不能用“知悉风险”把它改成完全响应；内部台账始终保留原事实。

### 待核验

草稿可使用：

> 【待产品/交付/商务确认：需确认的具体问题、责任人、截止时间】

不得用“支持、可实现、后续提供”暂时代替。提交候选版中不得存在待核验状态和该类占位符。

### 不适用

> 该要求在本项目中不适用，依据为【招标范围、系统边界或已确认澄清】。为避免遗漏，我方仍采取【必要的衔接或风险控制】。

“不适用”是适用性判断，不是能力状态。必须有来源依据并记为 `不适用已确认`，不能仅因编写困难而使用。

## 评分项响应单元

每个评分项先在内部完成以下结构，再转化为正文：

1. 评分原文和 `score_id`；
2. 满分动作、满分内容、满分证据、满分形式和门槛；
3. 对应章节、图表、证明材料和附件位置；
4. 每个满分条件的完成状态；
5. 可能扣分点及补救；
6. C+ 评委追问和回答依据。

正文应让评委能按评分原文逐项勾选。建议小节标题复用评分关键词，但不要把“预计得分”或内部风险判断写入投标文件。

对于主观评分项，使用“结论—设计依据—方案机制—项目化执行—风险控制—验收证据”展开；对于客观计分项，优先使用简洁响应表和准确证明索引，避免用长篇叙述掩盖缺证据。

## 业务理解和总体方案

### 业务理解

从招标范围、现状材料和访谈事实提炼：

- 当前业务链条与参与角色；
- 影响项目成败的核心矛盾；
- 数据、流程、系统、管理和合规风险；
- 采购目标及其可验证结果。

不得把客户名称替换后复用其他项目背景。无法确认的现状写成“需在项目启动阶段核实的假设”，不写成事实。

### 总体方案

总体方案至少回答：

- 为什么采用该总体思路；
- 各层、各组件和外部系统如何协同；
- 数据、业务和管理闭环如何形成；
- 方案如何对应评分点和重点需求；
- 哪些是产品基线、项目配置、定制开发和第三方依赖；
- 如何实施、切换、验收和运维。

架构图必须与正文组件名、系统边界和部署方式一致。不得用通用“平台层—能力层—应用层”图替代项目逻辑。

## 功能和场景章节

功能章节优先按“业务场景或业务链条”组织，再在场景下响应功能点。每个场景说明：

- 触发角色和前置条件；
- 输入数据或材料；
- 系统处理流程和关键规则；
- 异常、回退和人工处置；
- 权限、日志和审计；
- 输出、状态变化和后续环节；
- 对应 `requirement_id` 和验收方式。

如果招标文件强制按功能清单顺序逐条响应，应保留原顺序和原描述，在旁列给出能力状态、实现说明、证据与章节索引；正文场景化方案作为深入说明，二者互相引用。

功能描述不是菜单罗列。例如“支持检索”至少要说明检索对象、字段和权限范围、结果过滤、日志、异常和验收；但不得在原文未要求且产品未确认时扩写智能推荐、秒级响应等能力。

## 专题技术章节

### 架构与部署

说明逻辑架构、部署拓扑、组件职责、网络边界、环境规格、扩缩容、容灾备份和运维界面。涉及高可用、并发、容量、RPO/RTO 等数字时必须关联已审批承诺。

### 接口与集成

对每个外部系统说明：

- 数据方向、触发方式和交换频率；
- 接口协议、认证、字段映射和错误码；
- 幂等、重试、对账、补偿和审计；
- 联调条件、责任边界和第三方依赖；
- 测试数据、验收场景和失败处置。

没有接口文档时，以“接口假设与待澄清清单”表达，不虚构接口地址和字段。

### 数据迁移

至少覆盖盘点、映射、清洗、试迁、校验、正式迁移、差异处置、回退、报告和责任分工。明确源数据质量、停机窗口和业务确认责任；迁移数量、速率和完成时限必须有依据。

### 安全与合规

把安全要求落到身份、权限、数据、接口、主机网络、日志审计、备份恢复、漏洞和应急处置。引用标准和等级时核对适用版本及项目范围，不把“遵循标准”写成“已通过认证”。

## 交付型章节

### 实施计划

以交付物和退出条件定义阶段，不只列时间轴。每个阶段至少说明：

- 输入条件；
- 关键任务和责任角色；
- 可检查交付物；
- 评审或验收门槛；
- 依赖和风险；
- 未通过时的处置。

工期必须与商务、人员、定制范围和招标节点一致。

### 测试与验收

测试用例要追溯到原子需求。说明测试环境、数据、角色、步骤、期望结果、缺陷分级、回归和报告。招标文件没有给出量化验收门槛时，不得擅自替招标人定义合同级门槛。

### 培训

按角色、任务和能力目标设计课程，而不是只列“系统培训”。说明对象、内容、方式、材料、考核、补训和知识移交；人数、课时、次数和地点属于承诺，须核验。

### 运维与服务

区分故障响应、问题解决、现场到达、恢复目标和服务时间，不混用概念。每个时限、覆盖期限、免费范围和服务方式都进入承诺台账，并与商务条款一致。

## 图表使用规则

图表只在能降低评审理解成本时使用：

- 多系统关系：架构图或集成关系图；
- 多阶段状态变化：流程图或泳道图；
- 角色与责任：RACI 表；
- 需求、章节和证据对应：追溯表；
- 计划和里程碑：里程碑图；
- 风险、触发条件和措施：风险表。

不得为了“显得专业”把连续叙述全部改成表格，也不得用表格模拟所有架构图。图内文字、正文术语和追溯矩阵必须一致。

## 工作稿、审查草稿与提交候选版

工作稿允许覆盖不完整和结构占位，但必须标注“未完成，不可提交”。

审查草稿可以保留结构化待确认项，但需求、评分项和重要条款映射必须达到 100%，且待确认项必须包含责任人和截止时间，不得用无责任的 `TBD` 或 `XX`。

提交候选版必须满足：

- 所有响应状态已关闭并与正文一致；
- 所有事实主张有来源或已删除；
- 所有承诺均为 `无需新增承诺`、`沿用采购要求` 或 `已审批`；
- 所有偏离已决策；
- 评分满分条件有明确落点；
- 不再出现内部批注、风险判断、预计得分和待确认标记。

## 反模式和自检

发现以下写法立即修订：

- **空结论**：“完全响应、完全满足”后没有机制、边界或证据；
- **功能堆砌**：把产品菜单复制成方案，没有客户场景和实施落点；
- **无依据量化**：“秒级、100%、大幅、显著、7×24”没有授权来源；
- **第三方伪装**：把生态伙伴、云服务或客户现有系统能力写成自有能力；
- **条件后置**：正文先无条件承诺，最后才写接口、数据和环境限制；
- **固定篇幅注水**：按页数重复背景、意义、原则和套话；
- **通用图替代方案**：图中组件无法对应本项目需求、部署和责任；
- **证据错配**：案例或证书存在，但不能证明当前评分项限定条件；
- **章节孤岛**：功能、实施、测试、验收、运维使用不同术语或矛盾数字；
- **商务越界**：技术章节擅自承诺免费范围、付款、违约或报价。

每完成一章，至少自问：

1. 该章对应哪些 `requirement_id` 和 `score_id`？
2. 满分条件能否被评委逐项找到？
3. 哪些句子构成事实或承诺，依据在哪里？
4. 条件、依赖和异常是否比“正常流程”更薄弱？
5. 该章与实施、测试、验收和运维能否闭环？
