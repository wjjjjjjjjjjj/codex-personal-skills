# 需求、评分、证据与承诺追溯矩阵

## 何时读取本文件

以下任一条件成立时读取：

- 招标文件包含技术需求、评分表、★/▲/# 条款或证明材料要求；
- 需要判断“是否逐条响应”“能否拿满分”或“是否存在虚假承诺”；
- 发生答疑、更正公告、产品能力变化或证据替换；
- 技术标进入提交候选版，需要计算覆盖率和关闭待确认项。

本文件定义数据结构和状态，不规定 Word 样式。

## 核心原则

正式响应必须从权威原文建立可定位的结构化摘录。摘要只能用于导航，不能替代招标文件、评分表、答疑和更正公告原文。

追溯关系不是“一条需求对应一段文字”，而是以下多对多关系：

```text
来源版本 → 原子需求/评分项 → 满分条件 → 响应章节 → 证据 → 承诺/偏离 → QA 结果
```

任何评分结论都必须能沿该链条回到“文件、版本、页码或表格行”；任何对外承诺都必须能回到已确认的能力或授权。

## 第一步：建立来源版本台账

每一份文件先登记，再抽取条款。

| 字段 | 必填 | 说明 |
|---|---:|---|
| `source_id` | 是 | 唯一编号，如 `SRC-001` |
| `source_level` | 是 | A/B/C/D/E，与 `source-and-claims.md` 的来源分层一致 |
| `文件名` | 是 | 保留原文件名 |
| `文件类型` | 是 | 招标文件、评分表、答疑、更正公告、招标模板、产品资料、案例、证书、合同边界、其他 |
| `发布/出具方` | 是 | 采购人、代理机构、产品部门、证明材料出具方等 |
| `版本/发布日期` | 是 | 无版本号时记录文件日期和收到日期 |
| `接收时间` | 是 | 本项目实际取得材料的时间 |
| `适用范围` | 是 | 项目、包号、产品版本、条款范围或证明主张 |
| `有效状态` | 是 | 见下方统一机器枚举 |
| `优先级` | 是 | 更正公告/答疑 > 原招标文件；同类文件以最新有效版本为准 |
| `替代关系` | 否 | 指向被替代的 `source_id` 和条款范围 |
| `文件指纹` | A/B/C 必填 | 原始文件 64 位 SHA-256；路径不能替代指纹 |
| `登记人/时间` | 是 | 可追责 |
| `备注` | 否 | 缺页、扫描件、表格错位等风险 |

发现同名不同版文件时立即阻断条款抽取，先确认有效版本。不得把旧评分表的内容静默合并到新版。

`source_register.json` 的 `status` 统一使用以下机器枚举，两份参考文件不得另建状态：

- `active`：现行有效；
- `partially_superseded`：部分被替代，必须在 `notes` 写明保留范围和替代范围；
- `superseded`：已被替代/已失效；
- `pending_confirmation`：效力待确认，不能用于提交候选版结论。

“仅供参考”属于 `source_type`、适用范围或优先级，不是生命周期状态。

来源角色必须与用途匹配：采购方权威来源用于证明“采购方要求什么”，不能单独证明“我方已经具备什么”；`已具备`、`条件具备`、`定制实现`、`第三方依赖`必须至少关联一条能力证据来源（产品资料、书面确认或其他已登记证据）。`沿用采购要求`则必须回链现行的招标、答疑、更正、采购需求或评分来源。

## 第二步：拆分原子需求并锁定独立基线

先把现行来源中的原子需求、标记、强制属性和评分原文写入
`source_requirements.csv`，再建立 `technical_traceability.csv`。前者是来源抽取基线，不能从
响应稿或追踪矩阵反推；后者只增加章节、能力、证据、承诺、偏离和复核状态。

提交模式下，两表 `requirement_id` 集合必须完全一致；共同字段
`parent_id/source_ref/requirement_text/requirement_type/marker` 必须逐项一致。删除响应矩阵行、
改写原文或抹去 ★/▲/#/* 标记均属于阻断。

### 原子需求定义

一个原子需求只表达一个可独立判断、独立响应、独立验收的义务。它至少包含：

- 一个动作或能力；
- 一个对象或范围；
- 必要的条件、约束或指标；
- 可判断的结果或证明要求。

出现以下情况必须拆分：

- 同一句中使用“并且、同时、以及、分别、至少包括”等连接多个义务；
- 一个条款同时包含功能、性能、安全、交付物或证明材料要求；
- 同一段中存在多个可分别扣分的评分条件；
- 一个要求包含多个角色、系统、数据对象、时间点或验收标准；
- “提供方案并提供案例/证书/截图”等内容与证明要求绑定。

不得拆分导致语义丢失。共用前提、范围或量化指标应复制到每条原子需求，或通过 `parent_id` 关联。

### 原子需求字段

| 字段 | 必填 | 说明 |
|---|---:|---|
| `requirement_id` | 是 | 唯一编号，如 `RQ-003-02` |
| `parent_id` | 否 | 上位条款或评分项 |
| `source_id` | 是 | 来源版本台账编号 |
| `原文定位` | 是 | 页码、章节、表格名与行号；扫描件可加图页号 |
| `原文` | 是 | 不改变义务边界的完整原文 |
| `需求类型` | 是 | 否决项、强制项、评分项、功能、非功能、集成、数据、实施、验收、服务、交付物、格式、证明材料 |
| `标记` | 是 | ★、▲、#、无；同时保留招标文件自定义含义 |
| `动作` | 是 | 建设、支持、迁移、提供、证明、承诺等 |
| `对象/范围` | 是 | 系统、模块、数据、组织、场景等 |
| `约束/指标` | 否 | 数量、并发、时限、标准、兼容范围等 |
| `验收/证明要求` | 否 | 测试、截图、证书、案例、演示、承诺函等 |
| `响应章节` | 是 | 章节编号或稳定锚点，不只写页码 |
| `适用性` | 是 | `适用`、`不适用待确认`、`不适用已确认` |
| `能力状态` | 适用时必填 | 见下文状态枚举；`不适用已确认` 时留空，并以适用性依据闭环 |
| `响应进度` | 是 | 见下文状态枚举 |
| `证据引用` | 视情况 | 在标准 CSV 中使用一个或多个 `source_id#定位`，多个值以分号分隔 |
| `承诺引用` | 视情况 | 关联 `commitment_register.csv` 中一个或多个承诺编号 |
| `偏离说明` | 条件必填 | 非完全支持时必填 |
| `责任人` | 是 | 产品、售前、交付、商务、法务等 |
| `复核状态` | 是 | 未复核、内容复核通过、证据复核通过、已锁定 |

标准模板 `assets/templates/technical_traceability.csv` 使用英文机器字段名，含义映射如下：

- `requirement_id/parent_id/source_ref/requirement_text`：要求编号、上位编号、来源及定位、完整原文；
- `requirement_type/marker/action/object_scope/constraints`：需求类型、标记、动作、对象范围、约束指标；
- `acceptance_evidence_requirement/response_section`：验收或证明要求、响应章节；
- `applicability/capability_status/capability_confirmer/capability_confirmed_at/response_progress`：
  适用性、能力状态、能力确认人、确认日期、响应进度；
- `evidence_refs/evidence_status/commitment_refs`：证据来源及定位、证据状态、承诺引用；
- `deviation_status/deviation_note/owner/review_status/notes`：偏离状态、偏离说明、责任人、复核状态、备注。

不得另加 `covered/partial/pending` 单值列覆盖上述联合状态。

### 能力状态

只能使用以下枚举：

| 状态 | 使用条件 | 是否可写“完全满足” |
|---|---|---:|
| `已具备` | 当前正式产品或现有交付能力已支持，且边界明确 | 仅在证据有效且无偏离时 |
| `条件具备` | 在明确版本、配置、数据、环境、接口或客户配合条件下支持 | 否 |
| `定制实现` | 基线产品不直接支持，需要本项目开发并已确认范围、责任和计划 | 否 |
| `第三方依赖` | 关键能力由第三方产品、服务或接口提供 | 否 |
| `不支持` | 当前能力或项目范围不能满足 | 否 |
| `待核验` | 尚无足够材料判断，或责任人未确认 | 否 |

`条件具备`、`定制实现`、`第三方依赖` 和 `不支持` 均必须说明依据、边界和影响。`不适用` 属于适用性判断，不是能力状态；只有取得招标范围、答疑或书面边界依据后，才能使用 `不适用已确认`。不得用“原则上支持、可支持、基本满足”规避状态判断。

`已具备 + 正偏离`是合法组合，但必须同时具备可定位的已核验证据、具体偏离说明，以及一条已审批、
无冲突、已作最终处置的承诺。追踪矩阵中的 `commitment_refs` 与承诺台账中的
`requirement_refs` 必须双向一致。正偏离不得伪装成普通“完全满足”，也不得用一条审批记录覆盖
不同对象、否定改写或新增无条件范围。

### 响应进度

按以下状态流转：

```text
未处理 → 已拆解 → 已起草 → 待证据/待确认 → 已复核 → 已锁定
```

- `待证据/待确认` 可返回 `已起草` 修订；
- `已锁定` 只允许因答疑、更正、能力变化或评审缺陷而解锁；
- 提交候选版不得存在 `未处理`、`已拆解`、`已起草` 或 `待证据/待确认`。

## 第三步：拆解评分满分条件

评分项必须同时保存原文和“满分条件”，不得只记录分值。

### 满分条件字段

以下字段必须保存在 `source_requirements.csv` 的来源基线中，不能只存在于章节蓝图或写作者笔记。

| 字段 | 必填 | 说明 |
|---|---:|---|
| `score_id` | 是 | 如 `SC-02-01` |
| `source_id/原文定位` | 是 | 指向评分表现行版本 |
| `评分原文` | 是 | 含分档、扣分、证明和格式要求 |
| `最高分` | 是 | 原始分值 |
| `评分方式` | 是 | 客观计分、分档评分、横向评审、主观评审、否决关联 |
| `满分动作` | 是 | 需要“提供、说明、承诺、证明、演示”的具体动作 |
| `满分内容` | 是 | 方案必须覆盖的主题和深度 |
| `满分证据` | 否 | 案例、证书、截图、承诺函、检测报告等 |
| `满分形式` | 否 | 表格、逐条响应、盖章件、指定章节或附件位置 |
| `数量/门槛` | 否 | 个数、等级、年限、参数或时限 |
| `扣分触发` | 是 | 缺项、弱响应、无证明、错放位置等 |
| `关联 requirement_id` | 是 | 一个评分项可关联多个原子需求 |
| `响应章节/证据_id` | 是 | 实际落点 |
| `满足状态` | 是 | `已满足`、`部分满足`、`未满足`、`待核验`、`不适用待确认` |
| `预计得分` | 否 | 仅作内部判断，不写入投标正文 |
| `风险与补救` | 否 | 缺证据、需澄清、需优化等 |

满分条件拆解以“能否被评委逐项勾选”为标准。例如“方案完整、合理、可行，得 4 分”至少拆为完整性主题、合理性论证、可行性措施及相应证明或实施约束，不能用一段“我方完全理解并满足”覆盖。

## 第四步：建立证据台账

证据用于支撑能力和主张，不等于把附件名称写进正文。

| 字段 | 必填 | 说明 |
|---|---:|---|
| `evidence_id` | 是 | 如 `EV-014` |
| `证据名称` | 是 | 产品手册、检测报告、证书、合同关键页、验收材料、系统截图等 |
| `source_id` | 是 | 所属文件 |
| `支撑主张` | 是 | 明确支撑哪项能力、指标或案例事实 |
| `关联 requirement_id/score_id` | 是 | 可多选 |
| `证据等级` | 是 | `原始权威`、`内部正式`、`项目材料`、`辅助说明` |
| `证据状态` | 是 | `已核验可引用`、`已取得待核验`、`待补证`、`证据失配`、`无证据`、`不适用` |
| `适用范围` | 是 | 产品版本、客户、项目、地区、时间等 |
| `正文引用位置` | 是 | 章节、附件或证明材料索引 |
| `脱敏/授权状态` | 是 | `可直接使用`、`需脱敏`、`需授权`、`禁止外发` |
| `复核人/时间` | 是 | 产品、法务或材料所有者 |

证据优先级不是绝对可信度排名；关键是能否直接支撑当前项目、当前版本和当前主张。辅助说明不得替代招标要求的指定证明。

## 第五步：建立承诺台账

正文中出现“确保、保证、达到、不低于、在……内完成、免费、终身、无条件、100%”等措辞时，必须登记承诺。

| 字段 | 必填 | 说明 |
|---|---:|---|
| `commitment_id` | 是 | 如 `CM-008` |
| `original_text` | 是 | 决策前拟写原文，作为审计轨迹保留，不得进入正文白名单 |
| `final_text` | 条件必填 | 保留、收窄或改为条件承诺后的最终措辞；正文必须与其一致 |
| `承诺类型` | 是 | 能力、性能、进度、SLA、资源、兼容性、服务、费用、验收、合规、其他 |
| `关联 requirement_id/score_id` | 是 | 来源义务 |
| `正文位置` | 是 | 章节或表格行 |
| `来源依据` | 是 | 招标强制要求、产品能力确认、交付确认、商务确认、合同边界等 |
| `量化值/单位` | 条件必填 | 数字、时限、比例、容量等 |
| `适用条件和排除项` | 是 | 环境、接口、数据质量、客户配合、第三方等 |
| `责任部门/确认人` | 是 | 不得只写“项目组” |
| `确认状态` | 是 | 见下文 |
| `冲突检查` | 是 | 与商务、报价、工期、服务方案是否一致 |
| `处置` | 是 | 保留、收窄、改为条件承诺、删除、升级确认 |

标准模板 `assets/templates/commitment_register.csv` 中：

- `original_text/final_text` 分别保存拟写原文和最终可用措辞；扫描器只对白名单中的 `final_text` 放行；
- `requirement_refs` 对应关联需求/评分项；
- `source_ref/evidence_refs` 使用 `source_id#定位`；
- `quantified_value/conditions/owner` 对应量化值、适用条件和责任部门；
- `confirmation_status/approver/approval_date/conflict_check/disposition` 对应确认状态、审批人、
  审批日期、冲突检查和处置。

`technical_traceability.csv` 中每个 `commitment_refs` 必须在本表存在，且对应承诺的
`requirement_refs` 必须回链同一需求；任一方向缺失都属于提交阻断。

承诺状态沿用以下统一枚举：

- `无需新增承诺`：仅描述经证实的现有能力，没有新增期限、指标或资源承诺；
- `沿用采购要求`：明确响应采购方原始要求，未主动加码；
- `已审批`：新增承诺已由有权责任人书面确认；
- `待审批`：拟作出新增承诺，但尚未获批，只能进入草稿；
- `禁止承诺`：责任方否决，或缺乏实现和履约基础。

与来源冲突或没有依据不是一种可接受的承诺状态，应在 `冲突检查` 和 `处置` 中登记并立即阻断。已撤回内容保留审计记录，但不得继续出现在正文。

`disposition=保留` 时两段文本应一致；`收窄` 或 `改为条件承诺` 时必须保留不同的
`original_text`，并在 `notes` 说明删减范围或新增条件。`删除` 时 `final_text` 必须为空。

原文没有量化值时，不得为了“有说服力”自行添加“秒级、100%、7×24、数小时缩短至几分钟”等数字。招标文件要求承诺但内部尚未授权时，应进入待确认清单，不得默认承诺。

## 第六步：登记偏离和问题

非完全响应项不得隐藏在正文中。偏离台账至少包含：

- `deviation_id`；
- 关联需求与评分项；
- 招标要求；
- 实际能力和差异；
- 影响范围；
- 替代方案或补救措施；
- 是否需要澄清；
- 对评分、报价、工期、验收和合同的影响；
- 决策责任人；
- 偏离状态：`无偏离`、`正偏离`、`条件响应`、`负偏离`、`待澄清`；
- 处置状态：`待决策`、`已接受`、`不可接受`、`已关闭`。

如果招标文件禁止负偏离，应把所有 `不支持`、`条件具备`、`定制实现` 和 `第三方依赖` 项提升为 P0 风险，由项目负责人决定投标策略，技能不得自行伪装成完全支持。

## 覆盖率和闭环指标

以“现行有效且适用”的条目为分母：

```text
技术需求覆盖率 = 已有明确响应章节的原子需求数 / 原子需求总数
评分项覆盖率 = 已完成满分条件映射的评分项数 / 评分项总数
强制条款覆盖率 = 已复核并锁定的技术否决项、★/▲/# 条款数 / 该类条款总数
证据覆盖率 = 已配置有效且适用证据的必需证据项数 / 必需证据项总数
承诺审批通过率 = 状态为“无需新增承诺、沿用采购要求或已审批”的承诺数 / 正文承诺总数
```

提交候选版要求：

- 技术需求覆盖率、评分项覆盖率、强制条款覆盖率均为 100%；
- 必需证据覆盖率为 100%；
- 承诺审批通过率为 100%；
- `待核验`、`部分满足`、`不适用待确认`、`待审批`、`证据失配`、`无证据` 项为 0；
- 每个正文技术结论都能映射到需求、评分或已确认方案目标，禁止“孤儿主张”。

## 答疑和更正后的增量处理

收到新文件时执行：

1. 登记新 `source_id`，确认生效日期和替代范围；
2. 将被替代条目标为“已失效”，保留旧内容和映射，不直接删除；
3. 仅重新拆解受影响的原子需求和满分条件；
4. 找出所有关联章节、证据、承诺、偏离和答辩问题；
5. 修订后检查旧条款残留和新旧数字冲突；
6. 未受影响内容保持锁定，避免全稿无差别重写；
7. 输出变更清单：新增、删除、修改、未受影响及需要重新确认的承诺。

## 最小示例

评分原文：“提供数据迁移方案，内容完整、措施可行，并提供类似项目证明，得 3 分。”

应至少形成：

- `RQ-012-01`：提供数据迁移范围和对象说明；
- `RQ-012-02`：提供迁移流程、工具、校验、回退和责任分工；
- `RQ-012-03`：说明方案可行性的环境、资源和风险控制；
- `RQ-012-04`：提供符合限定条件的类似项目证明；
- `SC-04-01`：把“完整、可行、类似项目证明”的满分条件分别映射到章节和证据。

若只有迁移流程而没有有效项目证明，状态必须是“部分满足”，不能因正文写得充分而判断为满分。
